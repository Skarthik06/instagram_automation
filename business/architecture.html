A

Recommended architecture

Four isolated stages, connected only by typed contracts. This is the mandatory separation (Spec §33): each stage can be tested, replaced, and scaled on its own, and a failure in one never corrupts another. The anti-pattern PDF → OCR → LLM → Instagram is explicitly rejected because it launders unverified text straight into public marketing.

1 · Extraction
  • Deterministic + local OSS
  • Text, tables, images
  • Bounding boxes + evidence
2 · Intelligence
  • API LLM (gpt-5-nano)
  • Structured knowledge
  • Validation · marketing · plan
3 · Rendering
  • Deterministic
  • Real images only
  • IG-spec slides + QA
4 · Publishing
  • Existing IG engine
  • Consumed via contract
  • Not rebuilt

The platform is the upstream intelligence layer. It ends at a JSON contract (§K); the current Instagram machine — accounts, hosting, Graph-API publish — is consumed, never replaced.

B

Open-source components (researched)

Selected for reliability on real brochures, not popularity. The recommended set is deliberately permissive-license only so the platform is commercially safe to ship.

Docling MIT

IBM's layout-aware document converter: reading order, tables, figures, and structured JSON with coordinates. Primary extractor for digital PDFs.

pdfplumber MIT

Character-level text + table extraction with exact bounding boxes. Deterministic cross-check against Docling. Already validated on DREAMZ in this repo.

PaddleOCR Apache-2.0

Strong multilingual OCR (incl. Indic scripts) for scanned/image pages and text-in-images. Primary OCR.

Tesseract Apache-2.0

Mature OCR fallback; already in the backend image via pytesseract.

OCRmyPDF MPL-2.0

Wraps Tesseract to make scanned PDFs searchable — normalizes messy scans before extraction.

pypdfium2 Apache/BSD

Google PDFium bindings for page rasterization + image extraction — the permissive replacement for AGPL PyMuPDF.

open_clip MIT

Local zero-shot image classification (building/interior/floor-plan/map/logo) — no API cost for the common cases.

OpenCV · Pillow Apache / HPND

Deterministic image ops: crop, resize, quality/blur scoring, perceptual-hash dedup. Already installed.

D

Document extraction strategy

A routed, measured cascade — never "OCR everything." Ingestion classifies the file; extraction picks the cheapest path that works and measures its own coverage.

  • Digital PDF (like DREAMZ): Docling for structure + pdfplumber for coordinate-exact text/tables. No OCR.
  • Scanned / image-only PDF: OCRmyPDF → PaddleOCR (Tesseract fallback). Trigger only when digital-text coverage is below a measured floor.
  • Office files (DOCX/XLSX/PPTX/CSV): native parsers (python-docx, openpyxl, python-pptx, csv) — deterministic, no LLM.
  • Loose images / screenshots / WhatsApp: OCR + Multimodal vision (§E).
Why this matters — proven on DREAMZRaw text came out as "NPS Viyaranyapura – 1Km ttings" (columns interleaved, "fittings"→"ttings") with ligature corruption (reects→"reflects"). Layout-aware extraction + glyph normalization + evidence binding is the difference between a fact and garbage.
E

Multimodal extraction strategy

Text and visuals are extracted in parallel and then bound to each other. DREAMZ alone carries a building render, a builder logo, a location map, a cluster plan, and a dimensioned floor plan — all embedded raster images.

  • Classify every image locally (open_clip zero-shot) into the asset taxonomy; deterministic dedup + blur/quality gating first.
  • Detect floor plans / maps / logos; read floor-plan dimension callouts, but flag image-derived numbers for verification (never auto-trust).
  • Bind each asset to the fact it evidences: {asset_type:"floor_plan", page:4, property_type:"2BHK", area_sqft:940, confidence:0.96}.
  • API vision (gpt-5-nano accepts images) is a bounded fallback for ambiguous/critical assets only — logged and budgeted, never the default classifier.

Real images are always preferred; the system never fabricates a building/interior to represent a real property (Spec §15).

F

Property knowledge schema

One normalized model for apartments, villas, plots, sites, land, commercial, rental, resale, and new projects. Configurations are a list (a project may offer several BHK/areas — never flattened). Every populated field maps to a claim with evidence; unknowns are the literal NOT_AVAILABLE.

Full JSON Schema: business/schema/property_knowledge.schema.json. Grounded DREAMZ instance (benchmark oracle): business/benchmarks/dreamz_expected.json.

claim = { field, value, confidence, source:{document,page,text|bbox,method} }
nearby = { name, distance, distance_kind: SOURCE_DOCUMENT_DISTANCE | CALCULATED_DISTANCE }
media  = { asset_type, page, bbox, quality, usable, confidence, source }
G

Evidence & validation architecture

Three deterministic-plus-LLM gates stand between "extracted" and "publishable":

  • Evidence binding — every fact keeps {document,page,text,bbox}; a fact with no locatable span is dropped.
  • Verification (Agent 05) — confirms the cited span entails the value (not mere co-occurrence) for key fields; scores confidence; catches hallucination.
  • Contradiction / "clashes" (Agent 06) — diffs shared fields across documents & versions; a real conflict → HUMAN_VERIFICATION_REQUIRED, never a silent pick.
CONFLICT DETECTED
  Field: configuration.area_sqft
  Source A: 940 sqft (docA p3)   Source B: 950 sqft (docB p2)
  Action: HUMAN_VERIFICATION_REQUIRED
H

Marketing intelligence algorithm

Not "write a caption." The strategist (Agent 07) reasons over the validated model to choose audience, selling points, and angle — each tied to a verified fact.

  1. Score angles deterministically by which verified facts are strong/present (budget? connectivity? floor plan? views?).
  2. LLM selects the winning angle ∈ {LOCATION, FAMILY, BUDGET, LIFESTYLE, AMENITY, CONNECTIVITY, SPACE, FLOOR_PLAN, BUILDER_TRUST} + rationale.
  3. Audiences only as data supports them — DREAMZ (budget 2BHK, park view, schools 500m–1km, metro 6km) → first-time buyers / young families → likely BUDGET_FIRST or CONNECTIVITY_FIRST.
  4. CTA matches the campaign goal: site_visit → "DM 'VISIT' to book a site visit".

No urgency, scarcity, guaranteed returns, or fabricated prices — ever.

I

Carousel generation algorithm

Multiple reusable strategies (Property Discovery, Location First, Family First, Floor-Plan First…), selected by angle + which assets/facts actually exist. Each slide is structured data with a real asset reference.

slide = { slide_number, template, headline, subheadline,
          facts[verified], image_ref[real], badges[], cta, theme, brand }
caption = { hook, body, key_points[], cta, hashtags[], location_tags[], keywords[] }

A slide whose required asset/fact is missing is dropped or marked needs_asset — the template never forces a floor-plan slide when no floor plan exists.

J

Rendering technology recommendation

Recommendation: HTML/CSS templates → Playwright screenshot, with Pillow/Sharp for crops and SVG for vector badges/icons.

Why
Rich, maintainable templates (grid, web fonts, gradients, map/floor-plan crops, price badges) that a designer can iterate in the browser — far beyond hand-placed Pillow draw calls.
Solves
The design-system requirement (Spec §14): 1080×1350 / 1080×1080, typography, brand, overlays, cards, CTA panels — pixel-exact and deterministic.
Alts
Pillow (keep for simple overlays; verbose for complex layout) · Fabric.js/canvas (client-side, heavier) · raw SVG (great for vector, awkward for photo composition).
Why now
Chromium already ships in the backend image (Playwright is installed for the current scraper) — zero new heavy dependency.
License
Playwright Apache-2.0 · Pillow HPND · both commercial-safe.

O

Failure cases (designed-for)

Extraction

  • Image-only PDF, no OCR text
  • Rotated / multi-column pages
  • Ligature/glyph corruption
  • Non-Latin scripts

Knowledge

  • Hallucinated price/RERA
  • Cross-document conflicts
  • Multi-config brochures
  • Missing critical fields

Visual

  • Text overflow / cut-off
  • Low-res hero image
  • Altered contact number
  • Near-duplicate slides

System

  • LLM budget exceeded
  • Cache miss storms
  • Review SLA breach
  • IG contract drift

Every case resolves to an explicit state (REVIEW_REQUIRED / REJECTED / error) — never a silent wrong answer.

P

Security & privacy

  • Documents carry PII (names, phones, addresses, ownership, legal) — treated as sensitive: encrypted at rest where appropriate, access-controlled, audit-logged, deletable, configurable retention.
  • No secrets in source/Git (env / secret store only — consistent with the existing .ragskey + git-ignored .env).
  • Minimal LLM payloads; never send whole documents or unneeded PII to any external API; never PII in URLs/logs.
  • Enforced continuously by the Security & Privacy agent (11) across every stage.
Q

Cost optimization

Local/OSS does the heavy lifting; the API LLM is a scalpel, not a firehose (Spec §28). Enforced by the Cost Governor (12).

  • Funnel: raw → local extraction → structured → only relevant slice → LLM. Whole documents are never sent.
  • gpt-5-nano, minimal reasoning — verified at $0.05/1M in · $0.40/1M out, with 0 reasoning tokens on structured tasks.
  • Cache by input hash; reuse one property's knowledge across all channels (§21) instead of re-parsing.
  • Per-campaign budget ceilings with a live spend ledger per property.
